## 已确认的执行开销

### 并发发生在文件之间

`test_core 0.6.16` 的默认公式为：

```dart
final defaultConcurrency = math.max(1, Platform.numberOfProcessors ~/ 2);
```

本环境由此默认运行 2 个测试进程。同一测试文件内部的用例顺序执行；提高 `-j` 不能让单个文件中的所有用例自动并行。`reader_exit_integration_test.dart` 位于 `test/`，名称中的 `integration` 不会将它变成 `integration_test/` 下的设备测试。

Flutter 的 `TestCompiler` 接收多个编译请求，但明确保证同时只编译一个请求。因此测试进程并发度与编译并发度不能混为一谈。工作流顶层的 `concurrency` 用于管理工作流运行的取消/互斥，也不等于测试用例并发。

### 全量覆盖率和编译启动都有固定成本

当前 CI 的范围分类主要决定是否启动 Flutter 任务；一旦启动，执行的仍是整套 `flutter test --coverage`。测试平台会为测试入口安排编译和测试设备启动，覆盖率收集器通过 VM Service 获取并合并结果。599 个文件意味着这些按文件发生的成本值得测量。

目前不能声称覆盖率占总耗时的一半、关闭后必然快几倍，或提高 `-j` 必然线性加速。上一轮没有 `--verbose` 的阶段计时，也没有同一批文件、同一缓存条件下带/不带覆盖率的对照。

## 测试价值与重构候选

| 候选 | 当前证据和后续判断 |
| --- | --- |
| 大型测试文件 | 阅读退出文件集中许多独立职责，是拆分候选；拆分时必须保留自定义 binding、全局状态及数据库的隔离和清理 |
| 重型夹具覆盖完整参数矩阵 | 阅读模式、章节、方向等组合复用完整数据库/图片夹具；应逐项判断哪些只需纯策略或轻量组件测试，哪些必须走真实链路 |
| 断言质量不足 | 旧封面测试检查提示、无障碍和尺寸，却没有检查实际页码文字矩形，因而未拦住重叠；`dee61e8` 已补齐相关断言。这不表示原语义检查本身无用 |
| 固定事件次数等待 | 旧图片监听测试只推进一帧就断言原生解码结果；已改为等待实际交付。后续审查同类写法，不能简单将所有超时调大 |
| 真实进程和恢复测试 | 数据导入崩溃测试会启动进程、强制终止并验证重启恢复。成本较高，但对应数据完整性，不能仅因耗时删除 |
| 过细的文件拆分 | 更多文件可能增加编译、启动及覆盖率成本；拆大文件与合并小文件应结合阶段数据，不能采用“文件越多越快”的规则 |

当前没有经过逐条审查或变异测试确认的“可删除测试清单”，也没有去重后的节省时间估算。

## 后续恢复顺序

用户重新安排测试性能工作后，按以下顺序接续：

1. 对比当前 HEAD 与本文基线。优先检查锁文件、Flutter SDK、测试配置、CI 命令及重点夹具是否变化；未变化的结论直接复用。
2. 选定同一批代表文件，包括纯逻辑、小组件、真实数据库/图片和进程恢复。记录缓存冷热状态及资源配额，避免对比不同文件集合。
3. 小范围运行四种组合：`-j2`/`-j4` 分别配合带/不带 `--coverage`。用 `--verbose` 获取 Flutter 阶段统计，用机器可读报告取得测试事件；同时记录整条命令墙钟时间和峰值内存。阶段可能重叠，不能直接相加。必要时重复取得中位数，再决定是否扩大测量。
4. 根据数据选择拆分大文件、减轻夹具、调整代表性组合或合并过细文件。每项保留原行为的替代断言；纯 Dart 测试还需核对传递依赖，不能直接把整套命令换成 `dart test`。
5. 再评估 PR 受影响模块加核心回归、完整覆盖率放定时/合并门禁、跨作业分片等方案。它们是待决定的策略，不是本轮已批准或实施的变更。
6. 先跑受影响回归，再按最终范围验收一次，更新本文、登记表与迁移记录。不得把分批补跑写成单轮全量通过。

长命令从启动时重定向日志，使用完成等待；完成后一次读取摘要，失败时再定向提取片段。用户已要求使用最长 600 秒的等待窗口；实际工具有更小上限时按工具上限等待，不为查进度反复读取日志。
